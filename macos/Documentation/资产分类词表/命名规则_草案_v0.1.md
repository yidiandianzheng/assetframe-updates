# 命名规则草案 v0.1（基于 18,480 条素材文件名实测）

状态：**草案**，供「导入后按分类 + 相似文件自动命名」设计使用；未接入 App、未修改数据库或素材、未安装依赖、未调用联网 AI。
统计日期：2026-10-22。配套机器可读数据：`命名规则_数据.json`（同目录）。上游词表：`词表_v0.1.json` / `README.md`（同目录）。
本文件只覆盖**文件名与来源路径**，不包含图片内容识别，也不代表用户确认。

## 0. 结论速览

1. **两款库合计 18,480 条素材，其中图片 3,111 张**（香万家木兰 2,565、古代种田 546）；本报告的命名统计一律以这 3,111 张图片为主，视频 1,343 条单列，文档 12,824 条不适用图片命名规则。
2. **无意义命名比想象中多**：按任务列举的严格口径（微信图片\_、IMG\_、ChatGPT Image、截图、未命名、纯数字）为 **103 / 3,111 = 3.3%**；若把机器导出名（slide\_01、frame\_、contact\_、final\_、icon、logo、image10、cover…）也算入，升至 **1,101 / 3,111 = 35.4%**；**完全不含任何中文字符的图片名 1,394 条（44.8%）；A+B+C+F 四类合计 1,493 条（48.0%），其中部分（如「微信图片」「未命名」）仍含中文**。
3. **已有的好命名有明确语法**：`_` 分隔（81.5%）、状态词（候选/已确认）在版本前、`vNN` 收尾（版本名的 83.4% 位于末段）。中文结构化名占 35.5%，且有中文的图片名合计 52.0%。
4. **两个库风格差异极大**：香万家木兰的 `/Volumes` 客户储存来源 84.3% 是原始/机器名；古代种田的 `/Volumes/02-AI创作` 来源结构化率 64.0%、Obsidian 项目位 85.3%；古代种田整体结构化率 70.9%，香万家木兰只有 28.0%。
5. **推荐模板**：`[项目_]{类型}_{主体}[_{视角或变体}][_{用途}]_{状态}_v{NN}`，至少含 `类型_主体_状态_vNN`；重名先查内容指纹，内容不同时版本号 +1，仍冲突加 8 位指纹后缀；判断不了用 `待分类_YYYYMMDD_序号`。
6. **注意口径边界**：文件名里的「已确认/定稿/最终」只是历史用词，**不能当作真实确认**；自动命名不得自行写「已确认」。

## 2. 分隔符与段数（图片，n=3,111）

### 2.1 分隔符出现率

| 分隔符 | 香万家木兰（2,565） | 古代种田（546） | 合计（3,111） |
| --- | ---: | ---: | ---: |
| `_` 下划线 | 2,076（80.9%） | 461（84.4%） | 2,537（81.5%） |
| `-` 连字符 | 241（9.4%） | 114（20.9%） | 355（11.4%） |
| 空格 | 53（2.1%） | 1（0.2%） | 54（1.7%） |
| `｜` 全角竖线 | 12（0.5%） | 1（0.2%） | 13（0.4%） |
| 括号 | 21（0.8%） | 1（0.2%） | 22（0.7%） |
| 不含任何分隔符 | 271（10.6%） | 84（15.4%） | 355（11.4%） |

要点：

- **`_` 是事实标准**；空格几乎不用；`-` 主要出现在编码（`SC-001`、`PR-002`、`AI-001`）与英文词（`Work-Fisher`）中，日期式 `2026-10-15` 也有。
- **`｜` 是视频专属惯例**：全素材中 479 条视频含 `｜`，图片只有 13 条。图片自动命名不要引入 `｜`。
- 括号主要是 `(2)`、`（版本1）` 这类副本/旧格式标记（图片 22 条），新命名不建议使用。

### 4.1 版本

| 指标 | 香万家木兰 | 古代种田 | 合计 |

| 3 位版本 | 5 | 0 | 5 |
| 最大版本值 | v46 | v10 | v46 |

| 状态词紧邻版本前 | 257（33.2%） | 320（82.9%） | 599（51.6%） |

结论：**`v` + 两位数字、放在最后**是主导写法（`候选_v01`、`已确认_v02`）。一位写法（v1/V1）只在旧素材出现，新命名统一两位补零；版本号只用于排序与避重，**不代表当前稿**。

## 7. 模板草案

### 7.1 语法

```text
[项目_]{类型}_{主体}[_{视角或变体}][_{用途}]_{状态}_v{NN}
```

- 最小必需：`类型_主体_状态_vNN`（例：`场景_陈家三房农舍_已确认_v04`）。
- 字段顺序：项目（可选）→ 类型 → 主体 → 视角/变体（可选）→ 用途（可选）→ 状态 → 版本。
- 分隔符统一 `_`；不用空格、不用 `｜`、不用括号；`-` 只允许出现在编码内部（`SC-001`）或日期中。
- 扩展名跟随源文件；**自动命名只生成素材库显示名（name），磁盘文件与 `originalFilename` 不改**，用于回溯。
- 若现有名已符合模板且无冲突，**保持原名**（如 `人物_温砚_真人试装参考_候选_v01`），不要为了统一而丢掉已有人工语义。

### 7.2 字段来源

| 字段 | 必填 | 取值来源（优先级从高到低） | 词表维度 |
| --- | :---: | --- | --- |
| 项目（可选） | 否 | 同项目已有文件名前缀（`木兰姐_`、`海南红茶_`）；sourcePath 项目目录；仅跨项目同主体冲突时使用 | — |
| 类型 | 是 | ① 词表分类结果（asset_type）② 同目录/相似文件的类型前缀 ③ 目录名映射 ④ 人工输入/复核 ⑤ 兜底「待分类」 | asset_type |
| 主体 | 是 | ① 词表 entity 标准名（许长山/温砚/陈家三房农舍/木兰姐/海南红茶…）② 原文件名主体词 ③ 目录名/相似文件 ④ 人工输入 ⑤ 兜底「待补充」 | entity |
| 视角或变体 | 否 | ① 词表 shot 值（正面/侧面/背面/俯视/四视图/宫格/全身/半身/近景/中景/特写/远景/全景/横屏/竖屏/白底…）② 原文件名描述段 ③ 相似文件修饰段 ④ 人工输入 | shot |
| 用途 | 否 | 词表 usage 的用途词（主图/补图/参考）+ 目录用途（封面/详情页/上屏/验收）；不在词表内的用途词按项目扩展并标来源 | usage |
| 状态 | 是 | ① 人工确认记录（**唯一**可写「已确认」的来源）② 导入默认「候选」③「历史停用」 | usage |
| 版本 | 是 | 同「项目+类型+主体+视角+用途+状态」组合现有最大 `vNN` + 1；无法归组时用指纹后缀 | — |

### 7.3 状态与版本的硬规则

- 状态只允许 **候选 / 已确认 / 历史停用**（与项目《人物资料标准》的确认口径一致）。
- **不允许**由文件名或自动命名推断「已确认」；原名里的 `已确认/定稿/最终` 只保留在 `originalFilename`，不迁移进新名。
- 版本格式 `vNN`（两位补零）；旧名 `v1/V1` 保留原值不回写；迁移旧素材时保留原 `vNN`，新导入从 `v01` 起按冲突递增。
- **版本号不代表当前稿**；确认以确认记录 + 文件指纹为准（引用《人物资料标准》）。

### 7.4 字符与长度

- 字符集：中文 + 数字 + 字母 + `_`；禁止 `/ \ : * ? " < > |`、制表符、表情符号。
- 归一化：Unicode NFC、去首尾空白、大小写不敏感比较（APFS 默认不区分大小写）、连续分隔符合并。
- 长度：实测图片名中位 19 字节、p90 56、最长 106 字节；结构化名中位 48、p90 65、最长 106。建议**目标 ≤ 80 UTF-8 字节、硬上限 120 字节**，超长时保留 `类型/主体/状态/vNN`，截短中间变体段。
- 画幅写法统一 `16比9 / 9比16 / 4比3 / 3比4 / 1比1`。现有 179 张图片含画幅标注且写法混用：`N比M` 77 处、`NxM` 69 处，另有 33 处其实是画布像素尺寸（如 `80x14`、`25x15`），自动命名不应把它们当画幅。

## 8. 重名与冲突（实测）

### 8.1 同名文件

| 指标（图片 3,111） | 数值 | 说明 |
| --- | ---: | --- |
| 同库内同名文件组数 | 413 组 | 同一库内 `originalFilename` 完全相同 |
| 同名多余条数 | 959 条 | 占图片总数 **30.8%**（香万家 914、古代种田 45） |
| 其中：同名且内容指纹相同 | 190 组 | 真正重复的内容，应关联而不是再命名 |
| 其中：同名但内容指纹不同 | 223 组 | **同名不等于同内容**（如不同 PPT 导出都叫 `slide_01.svg`） |
| 内容指纹（SHA-256）重复 | 450 组 / 多余 722 条 | 占图片 23.2%；含改过名但仍同内容的情况 |
| 同 basename 不同扩展名 | 47 组 | 多为 png+svg、png+jpg、psd+png 的色卡/设计稿（香万家 44、古代种田 3） |
| 两库之间同名图片 | 0 个 | 跨库未做内容去重，仅同名无交集 |

同名 Top 例：`slide_01.svg` 在 17 个目录各出现一次（同名不同内容），`cover.jpg` 4 次，`S16.svg` 3 次。**实现时不能只按文件名判重，必须查 `contentFingerprint`。**

全部素材（18,480）同名文件：2,972 组、多余 5,968 条；按 kind 分布——文档 1,896 组 / 4,216 条多余、图片 413 / 959、视频 357 / 401、其他 299 / 384、音频 6 / 6、字体 1 / 2。文档同名以工作区多目录的同构文件为主，属正常现象，不影响图片命名。

### 8.2 `name` ≠ `originalFilename`（被改过名）

- **图片：0 条**（2,565 + 546 全部 `name` = 去扩展名的 `originalFilename`）。
- **全部素材：6 条**，全部是「其他」类型的 `.修改前备份` 文件，`name` 为空，不是人工改名：
  `manifest.json.修改前备份`、`木兰姐_常用确认资产库.md.修改前备份`、`第07集_女儿比爹会挣钱_问路开场衔接_候选_v16.md.修改前备份`、`00_先读我.md.修改前备份`、`00_剧集索引.md.修改前备份`、`故事大纲.md.修改前备份`。
- 结论：库里**没有可参考的人工改名记录**；自动命名是「新起名」而不是「沿用用户改过的名」，因此需要保留 `originalFilename` 以便回溯。

### 8.3 其他边界情况

- 大写扩展名：`JPG` 46 条（jpg 小写 335、jpeg 45）；比较与去重时扩展名统一小写，实际文件名不强制改。
- 异常名：1 条 ` .png`（仅空格，位于 `/…/木兰姐/AI资产/人物资产/4K资产/`），应按空名/无效名处理，走兜底命名。
- 视频同名：357 组 / 多余 401 条，主要是同项目多轮导出（`(1)`、`V2/V3` 等），属制作过程产物，不影响图片规则。

## 9. 冲突处理与兜底命名

### 9.1 冲突处理（按顺序执行）

1. **归一化比较**：NFC、去空白、扩展名小写、全角/半角统一、大小写不敏感。
2. **先查内容指纹**（`contentFingerprint`，SHA-256）：相同 → 视为重复内容，**不生成新素材名**，提示已存在并可建立关联。实测图片内容级重复 **450 组 / 多余 722 条（23.2%）**，其中同名同内容 190 组、同名不同内容 223 组——**同名不等于同内容**，必须查指纹。
3. **同名不同内容、且属于同一「类型+主体+视角+用途+状态」组合** → 版本 `vNN` 自动 +1（取该组合现有最大值）。
4. **组合不同仍冲突** → 追加 `_h{contentFingerprint 前 8 位小写}`（如 `_h3f9a2c1b`）。
5. **同 basename 不同扩展名**（实测 47 组，多为 png+svg、png+jpg 的色卡/设计稿）→ 共用 basename、扩展名区分，**不追加序号**。
6. 最后手段才用 `(2)` 副本序号；新命名不使用（旧数据 22 条，排序与解析都更差）。
7. 大写扩展名（`JPG` 46 条）比较时统一小写；异常名（1 条，仅空格 ` .png`）按空名处理，用兜底名。

### 9.2 兜底命名（分类判断不了时）

| 档位 | 触发条件 | 格式 |
| --- | --- | --- |
| 1 | 类型、主体都可判断 | `{类型}_{主体}[_{视角}][_{用途}]_{状态}_v{NN}` |
| 2 | 有类型、无主体 | `{类型}_待补充_{YYYYMMDD}_{NNN}` |
| 3 | 有主体、无类型 | `{主体}_待分类_{YYYYMMDD}_{NNN}` |
| 4 | 都不判断 | `待分类_{YYYYMMDD}_{NNN}` |

- **日期来源**：优先从原名解析（微信 14 位时间戳、末尾 10 位 Unix 时间戳、中文日期、6 位视频日期），否则用 `sourceCreatedAt` 或入库日期。
- `NNN` 为三位补零序号，按同一入库日期/批次递增；生成前查同库已有名称避免二次冲突。
- 兜底名不携带内容猜测；`originalFilename` 永久保留，详情页可回看；分类补齐后可批量改名并保留历史。
- **注意**：`待分类`、`待补充` 是占位符，不是词表分类值；分类补齐后应替换。

### 9.3 工程产物（建议不自动命名）

`slide_01.svg`、`final_contact_01.jpg`、`frame-00-at-12.2s.png`、`contact_01.jpg`、`image10.jpeg` 这类图片是 PPT 导出、视频抽帧、联系表，属于**工作区工程产物**，不是内容素材。建议导入时过滤或标记「工程产物」，不进入分类词表自动命名；若必须入库，用 `工程_{项目}_{用途}[_{序号}]` 并明确标为项目扩展类型。

## 12. 限制与未验证项

1. **只覆盖文件名与来源路径**：不做图片内容识别、不调用联网 AI；新名中的「类型/主体」只能来自分类词表、目录或人工，不能从本报告推断图片内容。
2. **文件名状态 ≠ 真实确认**：原文件名里的「已确认/定稿/最终」不构成本轮确认依据；按项目《人物资料标准》，确认以确认记录 + 文件指纹为准，本报告未读取/核验确认记录。
3. **没有人工标签可交叉验证**：两库 tags/note/rating 全空；无法验证命名语义是否正确。
4. **没有改名历史**：`name` 基本等于去扩展名的 `originalFilename`（图片 0 条例外），无法还原用户过去的命名偏好。
5. **风格分类是启发式的**：A–F 六类由正则 + 人工定义，边界样本（`logo.png`、`cover.png`、`F01_说明脚注`、`S16.svg`）存在归类歧义；「无意义」不等于用户认为无意义。
6. **目录只是弱证据**：`sourcePath` 是导入时路径，可能已移动/改名；由目录推断的类型需人工或 AI 复核。
7. **数据是 2026-10-22 快照**；两库内容变化后需重新统计（口径见 `命名规则_数据.json` 的 `reproduction` 节，可只读复算）。
8. **模板与示例是草案（proposal）**，未接入 App、未改代码、未改数据库、未经用户确认。
9. **需用户拍板的事项**：状态词口径（是否只留候选/已确认/历史停用）、工程产物是否过滤、旧素材是否批量改名、项目段何时启用。
10. **未验证真实流程效果**：新命名的可读性、可检索性、用户接受度，以及「100 条真实导入抽样不重名、可回溯」的验收，需在接入后用隔离库（`/tmp/assetframe-qa.*`）验证。
11. **跨库未去重**：两库图片同名文件为 0，但内容仍可能重复；本轮未做跨库去重。

## 1. 复用同一套候选框架（没有新建第二套）

箱、建议、决定、撤销全部沿用工程里已有的标签建议机制，只是把「分类」作为新的建议种类接进去：

| 复用的类 | 原来负责什么 | 本轮怎么用 |
| --- | --- | --- |
| `MaterialTaggingState`（`+Suggestion` / `+Decision`） | 素材标签建议与用户决定的唯一状态容器，按节持久化 | 分类建议直接作为 `Suggestion` 存入同一 `suggestions` 数组，新增 `dimension`／`groupKey`／`engine`／`basis`／`isNewTerm` 字段，不另开状态类 |
| `MaterialDatabase` 的分节 BLOB 表 | `tagging_*` 各节首次显式保存才建表 | 建议与决定分别落 `tagging_suggestions`／`tagging_decisions`，与其他节同一套读写与损坏保护 |
| `MaterialTaggingUndo` + `MaterialUndoPatch` | 标签建议的撤销补丁，节名 `.suggestions`／`.decisions` | 四个操作与整批采纳都走同一撤销栈，未新增撤销类型 |
| `GlobalMaterialStore.changeTagging(_:undoable:)` | 建议状态的唯一写入口 | 所有建议写入（扫描、采纳、改名、忽略、拆分、合并、整批）都经这一个入口 |
| `ClassificationVocabulary` | 维度与标准词／别名表 | 建议名一律先查词表；查不到的仍给出建议但标 `isNewTerm`（界面显示「新词·待确认」） |
| `GalleryAutoClassifier` | 目录名／文件名的命名规则取词 | 规则引擎的建议来源，未改词表与判定口径 |
| `LocalImageClassifier`（macOS 自带 Vision） | 本地图像识别 | 空资产类型图片的分类名候选，不联网、不调线上模型 |
| `ProjectImageIndexer.featurePrintData` + 距离阈值 0.35 | 既有特征指纹与相似判定 | 空资产类型图片的分组依据（`basis` 里的「相似图」），未新建向量库 |
| `MaterialThumbnailView` | 卡片缩略图 | 建议卡片复用同一取图视图，未新增预览管线 |

### 4.4 决定持久化与重跑沿用

- 退出 App 后直接读库：建议与决定行都在（`库状态退出后.json`）。
- 重启后箱面板仍显示同一批建议，「重开后决定仍在」「重开后界面仍能看到建议」两项为真。
- 重启后再点「扫描命名规则」：已忽略的组**没有重新回到待确认**，已采纳的组也没有重复提问；`重跑沿用既有决定` 为真。
- 用户手工值不被自动结果覆盖：这一条由 `ClassificationSuggestionSelfTest` 的「never-overwrite gate」断言覆盖（自测通过），本轮**未实机**验证（隔离副本里没有可区分的手工值样本）。

### 4.5 空资产类型分组与新词

对没有 `asset_type` 值的图片，用既有 `featurePrintData` 两两比较（阈值 0.35）分组，命名优先取词表（`ClassificationVocabulary`），词表外的名字保留但 `isNewTerm = true`。本轮副本库实测箱内 32 组按引擎分布为 **规则 1／本机视觉 4／相似图 27**（第 2 轮 V261023.10 采到，第 3 轮 `--skip-similarity` 复用同一批箱内产出）；全程未联网、未调线上模型，只用本机 Vision。

- **「不全库重跑」实测到**：那一趟的 `total` 恰好等于本次导入的图片数（307／1507），不是副本库的 2904／4411 张全量。代码取的是 `materials.filter { !idsBeforeImport.contains($0.id) }`（`GlobalMaterialStore.swift:895`）→ `indexImportedImages`（`ClassificationSuggestionStore.swift:63-79`，`guard !images.isEmpty, canWrite, !isSessionPaused`）。
- **自动结果只进箱**：三轮新增 3321 条记录里 `asset_type` 非空 0 条；同一时刻箱内 `道具／人物角色／色卡` 三组涨到 12／8／8 张，把握度 中／低／高、依据 `目录名`／`目录名`／`文件名`（第 2、3 轮 `规则引擎有进箱` 读数）。三组的成员不全是本轮新图（还含 22:48 诊断轮的 11 张），所以「成员全是本次新图的规则组」为 0 条——这正说明增量是**并回**已有同组（`unionWithExisting`），不是把整组顶掉。
- **逐张中间值没采到**：规则那一趟在一个采样间隔内就跑完了（第 3 轮 42 条读数里非零值只有一种：1507/1507；第 2 轮同理 307/307），且进度发布要 hop 回主线程（`Task { @MainActor in … }`），导入收尾一空闲就一次性追到最后值。所以任务书第 7 条那句「导入时显示进度，例如『已索引 120 / 300』」本轮**只实测到「按张累加的计数器与本次导入的范围」**，界面那行文字仍未实机看到；逐张上报由 `ClassificationSuggestionSelfTest` 的 `rule per-image progress` 断言覆盖。原因与「真正会被人眼看到的是相似图／视觉那一趟」见第 8 节第 12 条。

## 8. 本轮发现但没修的问题（等负责人裁决）

1. **拆分断言依赖「卡片序号 ↔ 面板排序」映射，这个映射不可靠。** 第 3 轮拆分写入成功（新组出现、决定表 +1），但按推算序号取的那条组张数没变——箱里 9 张的组不止一条，AX 遍历顺序与面板排序不保证一致。已把探针断言改成「整表前后差集」（哪条组真的减了张数、减的是不是新组张数、撤销后是否逐组复原），**代码未改**，等产品侧确认拆分语义后再判：现在 `splitClassificationSuggestion` 会把勾走的 id 从来源组移除（`ClassificationSuggestionStore.swift:178`）并给来源组追加「已拆出 N 张」说明，所以差集应当非空。
2. **「导入」按钮的 AXPress 永远回 `-25204`。** 因为 `LibrarySession.chooseImport` 里是 `NSOpenPanel().runModal()`，动作不返回，AX 判定超时——控件是 `enabled: true`，面板窗口也确实出现（`导入素材或文件夹`，1261×448）。任何后续自动化都不能把这条返回当成「点不动」；探针已改为按面板窗口是否存在判定。
3. **安静模式下没法用键盘在 NSOpenPanel 里选路径。** `⌘⇧G` 以 `postToPid` 发给非激活进程不生效（实测「前往」文本命中 0 条）。导入实跑因此走工作区底部「待恢复的导入 …／继续此任务」——同一个 `importFiles` 代码路径，但不是鼠标选面板那条。要证明面板可用，只能像本轮这样截到面板窗口为止。
4. **`run-self-tests.sh` 的源清单缺文件问题（第 1 步记录 §6）已在本步补齐**：`MODEL_SUPPORT_SOURCES` 加了 `ProjectClassificationProfile.swift`／`ProjectClassificationParser.swift`，`COMMON_SOURCES` 加了 `GalleryAutoClassifier.swift`／`ClassificationSuggestionEngine.swift`，并把 `GlobalMaterialStore.swift + ClassificationSuggestionStore.swift` 收成 `GLOBAL_STORE_SOURCES` 复用。这样新增文件的自测能随主套件一起跑，不再需要临时脚本 `sed` 拼清单。
5. 用户手工值「永不被覆盖」**只由自测覆盖**，本轮没有实机样本；负责人若要界面级证据，需要单独造「手工值 + 规则命中同一张图」的副本。
6. 补齐源清单后，全量自测往前走了一项，随即暴露**既有**的第 10 项失败（`maintenance` 目标里的 `MaterialDocumentPreview.swift` 需要 SwiftUIMacros 插件，纯 swiftc 编不过，详见第 9 节）。基线上没人看到它，是因为套件更早时在 `MaterialPlayerPreviewSelfTest` 就中止了。本轮没修：它不属于分类流程，且修法涉及自测清单取舍，需负责人裁决。
7. **`qa_pids()` 原来按 `ps` 命令行匹配副本根路径，永远匹配不到残留实例。** 实例是 `Popen` 用环境变量 `ASSETFRAME_QA_DATA_ROOT` 指根的，`ps` 的 command 列里只有 App 自身路径。后果：旧实例没被关掉就继续占着副本库的 `.writer.lock`，新实例只能报「资源库已被其他会话占用」，`status` 里没有 `store` 节，两轮导入验收各白等十几分钟。现改为「命令行路径标记 ＋ `lsof` 持锁者」两路取并集（实跑验证：能列出 pid，TERM 后清零）。顺带一个**报表口径错误**：`旧进程已退出` 这项原来是在新实例起来并连上 CLI 之后才测的，那时新实例自己就是持锁者，所以恒为 `false`（此前一轮记的 `true` 属于真空真，不可信）；现改成同时记「启动前残留实例」列表和清零结果。
8. **本机 23:1x 之后不再给任何 App 提供辅助功能元素树。** `界面驱动 buttons --pid` 回 0 条、`texts` 回 `texts:0, windows:1`、`osascript` 用 System Events 查同一进程 `window 1` 报 -1719、Finder `count of windows` 为 0、`unhide` 回 `frontmost: loginwindow`、`pmset -g powerstate` 回 `UserIsActive 0`。所以这不是「按钮点不动」，也不是驱动丢了辅助功能权限，而是锁屏／闲置时 WindowServer 不给界面树。**后果**：拆分断言重跑（第 4 轮箱验收）与界面「已索引 x / y」那行的截图都要等负责人在解锁状态下重跑；本轮所有界面项一律记「不作判定」，不拿静态检查冒充实机。工具侧已加 `ax_alive()` 前置门（点任何按钮之前先确认控件读得到），读不到就尽早收尾，不再空跑十几分钟。

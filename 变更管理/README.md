# 变更管理（同事优化 · 逐文件采纳 · 可回退）

本目录是给**负责人和同事协作改代码**用的轻量流程工具：同事在项目仓库的 `change/<变更ID>` 分支提交优化；负责人在 `main` 上**逐文件决定采纳/不采纳**；采纳后可随时回退（“回调”）。

> 一句话原则：**同事只推 `change/` 分支，负责人只在 `main` 上审核采纳；任何推送、打包、发布都由人手动确认。**

---

## 1. 目录与文件

```
变更管理/
├── README.md                 # 本说明
├── 索引.md                   # 所有变更的总表（脚本自动维护）
├── 模板/
│   └── 变更单.md             # 新变更的初始模板
├── 工具/
│   ├── _common.py            # 公共库（不要单独运行）
│   ├── 新建变更.py
│   ├── 提交变更.py
│   ├── 审核应用.py
│   ├── 回退变更.py
│   └── 自测.py
└── 记录/
    └── <变更ID>/             # 每个变更一个目录，随提交进入仓库
        ├── 变更单.md         # 目标、逐文件说明、采纳状态、风险、验证
        ├── 清单.json         # 机器可读的文件清单、基线 commit、分支
        ├── 改动.diff         # 本次完整 diff（人工审阅用）
        └── 应用记录.json     # 采纳后生成；回退依据（含应用前提交）
```

`索引.md` 的列固定为：**编号｜负责人｜日期｜目标｜状态｜采纳文件数｜回退时间｜记录链接**。
状态只能是：**待提交 / 待审核 / 已采纳 / 部分采纳 / 已回退 / 不采纳**。

## 2. 角色与职责

| 角色 | 做什么 | 不做什么 |
| --- | --- | --- |
| **同事（改动提交者）** | 从最新 `main` 新建 `change/<变更ID>` 分支；只改与目标相关的文件；填写逐文件说明；本地提交；push `change/` 分支；通知负责人审核 | 不推 `main`；不合并 `main`；不提交安装包/验证证据/用户数据/密钥；不直接改 `索引.md` 或别人的记录 |
| **负责人（采纳决策者）** | 拉取分支；逐文件标注「采纳/不采纳」；`--dry-run` 预演；正式应用并本地提交 `main`；需要时重新打包安装；不满意随时回退 | 不把未审核的分支直接合入；不跳过构建检查（涉及 Swift 时）；不把流程用于发布上传 |

> 同一时刻同一文件只应由一个角色修改；同事改代码，负责人改「采纳状态」列。

## 3. 环境要求

- macOS（本机已验证 macOS + Apple Git 2.54 + Python 3.9）。
- `git` 可用；项目仓库 `origin` 已配置（`yidiandianzheng/assetframe-updates`，源码与安装包同一个仓库）。
- `python3`（3.8+，只用标准库，无需安装任何依赖）。
- 涉及 `.swift` 改动的审核需要 Swift 工具链（Xcode / Command Line Tools）；若无工具链，请在负责人确认后使用 `--no-build` 并自行完成构建验证。
- 脚本**不联网、不自动 push、不自动打包/发布**；`git fetch / pull / push` 一律由人手动执行。

## 4. 首次接入（同事）

### 4.1 克隆仓库并配置身份

```sh
git clone https://github.com/yidiandianzheng/assetframe-updates.git
cd assetframe-updates
git config user.name "你的姓名"
git config user.email "你的邮箱"
git switch main
git pull --ff-only
```

> 需要仓库访问权限；首次配置建议只写本仓库（`git config`，不要 `--global`），避免影响其它项目。

### 4.2 检查工具可运行

```sh
python3 变更管理/工具/新建变更.py --help
python3 变更管理/工具/自测.py          # 可选：在 /tmp 里跑一遍完整流程，验证工具可用
```

### 4.3 新建变更

```sh
# ID 规则：CHG-年月日-当日序号（两位），例如 CHG-20261023-01、CHG-20261023-02
python3 变更管理/工具/新建变更.py \
  --id CHG-20261023-01 \
  --owner "张三" \
  --goal "优化素材导入时的重复检测逻辑"
```

脚本会：

1. 校验编号格式、当前在 `main`、工作区干净、分支/记录不重复；
2. 从当前 `main` 创建并切到 `change/CHG-20261023-01`；
3. 生成 `变更管理/记录/CHG-20261023-01/变更单.md` 与 `清单.json`；
4. 在 `索引.md` 里加一行（状态：待提交）。

> 工作区必须干净（没有未提交修改、没有未跟踪文件）。如果确实有临时文件，请先自己 `git stash` / 提交 / 删除，**不要**让脚本替你处理。

### 4.4 修改文件并提交

```sh
# 1) 修改与目标相关的文件
# 2) 第一次运行：自动生成文件清单与逐文件表格（说明列是占位文字，退出码 1）
python3 变更管理/工具/提交变更.py --id CHG-20261023-01
# 3) 编辑 变更管理/记录/CHG-20261023-01/变更单.md，给每个文件填「说明」
#    保持「采纳状态」为 待定（这是负责人的决定）
# 4) 校验说明是否填齐
python3 变更管理/工具/提交变更.py --id CHG-20261023-01 --check-only
# 5) 再次运行，提交到 change 分支并打印 push 命令
python3 变更管理/工具/提交变更.py --id CHG-20261023-01
# 6) 手动执行脚本打印的 push 命令
git push -u origin change/CHG-20261023-01
```

说明也可以用文件批量提供（适合文件很多时）：

```sh
# 说明.json：{"相对路径": "说明文字"}
python3 变更管理/工具/提交变更.py --id CHG-20261023-01 --notes 说明.json
```

> `说明.json` 里可只写部分路径，其余仍从变更单读取；填齐后脚本才提交。路径相对于仓库根目录。

### 4.5 提交前检查清单（同事）

- [ ] 变更只包含本次目标相关的文件（`提交变更.py` 会列出未跟踪文件，确认没有误带）。
- [ ] 每个文件都写清楚「为什么改、改了什么、影响哪里」。
- [ ] 没有把安装包、`ProductValidation/` 证据、用户数据、密钥、示例库带进提交。
- [ ] 没有直接改 `main`、没有把 `main` merge 进 `change/` 分支（同步基线请用 `rebase`）。
- [ ] `git push` 后再通知负责人；分支名保持 `change/<变更ID>` 不变。

## 5. 负责人审核采纳

### 5.1 拉取并定位分支

```sh
git switch main
git pull --ff-only          # 建议先让本地 main 与 origin/main 一致
git fetch origin            # 拉取同事的 change/<ID> 分支
```

脚本会优先使用 `origin/change/<ID>`，其次使用本地 `change/<ID>`；两者不一致时会停止并要求 `--branch` 明确指定（避免审错对象）。

### 5.2 第一次运行：复制变更单

```sh
python3 变更管理/工具/审核应用.py --id CHG-20261023-01
```

首次运行会把变更记录从 `change/` 分支复制到当前 `main` 工作区，提示你逐文件标注「采纳状态」，退出码 1（不是错误，属于流程提示）。

### 5.3 逐文件标注，然后预演

编辑 `变更管理/记录/CHG-20261023-01/变更单.md`，把每个文件的「采纳状态」改成 **采纳** 或 **不采纳**（不允许留「待定」）：

```sh
python3 变更管理/工具/审核应用.py --id CHG-20261023-01 --dry-run
```

`--dry-run` 会完整校验（分支、基线、清单一致性、标注、main 冲突、构建需求）并打印将采纳/不采纳的文件，但**不写文件、不构建、不提交**。预演通过后再正式运行。

### 5.4 正式应用

```sh
python3 变更管理/工具/审核应用.py --id CHG-20261023-01
```

脚本会：

1. 再次校验基线、清单与逐文件标注；
2. 只把「采纳」的文件按 新增/修改/删除/重命名 正确应用到 `main`；
3. 若涉及 `.swift` 文件，先执行 `swift build -c release` 构建检查；
   - **构建失败：自动恢复工作区、不提交**，你调整标注（或请同事修复）后重试；
4. 提交：`采纳变更 <ID>: N/M 个文件`（N=采纳数，M=变更总数）；
5. 更新 `记录/<ID>/应用记录.json` 与 `索引.md`（状态：已采纳 / 部分采纳 / 不采纳）；
6. 打印 push 命令与回退命令。**不会自动 push**。

### 5.5 推送与交付

```sh
git push origin main        # 确认有授权后手动执行
cd macos && ./package-app.sh    # 需要生效时重新打包（见第 8 节）
```

## 6. 逐文件采纳规则

建议按以下标准逐文件判断：

| 情况 | 建议 |
| --- | --- |
| 直接服务于本次目标、风险可接受、能通过验证 | 采纳 |
| 顺手的无关重构、命名风格调整、日志/注释噪声 | 不采纳（可让同事拆成单独变更） |
| 依赖外部服务/密钥/新依赖/网络行为 | 先确认授权与环境，否则不采纳 |
| 改动了用户数据、数据库结构、安装包、证据目录 | 不采纳（这些应走单独流程/单独授权） |
| 只采纳一半会导致编译失败/运行不一致 | 要么整体采纳，要么整体不采纳，或让同事拆成可独立验证的两批 |
| 涉及 `.swift` 且构建失败 | 不采纳或退回修改，直到构建通过 |

规则：

1. **每个文件都必须有明确结论**（采纳/不采纳），不能留「待定」。
2. 说明列由同事填写，负责人只在确实需要补充审核理由时追加，不改写同事的技术说明。
3. 一次变更内文件尽量少而聚焦；跨多个模块的大改动建议拆成多条变更，便于逐文件回退。
4. 拿不准时先 `--dry-run`，或只采纳能独立构建/验证的子集（脚本只应用采纳的文件）。

## 7. 部分采纳的风险（务必了解）

- **编译/测试风险**：只采纳 A 文件不采纳 B 文件，可能出现引用缺失、接口不一致；涉及 Swift 时脚本会构建检查，但构建通过≠功能正确。
- **运行行为不一致**：数据格式、资源路径、配置项成对修改时，只改一半可能导致旧数据无法读取。
- **回退粒度**：回退是“按变更整体回退已采纳文件”，不是按单个文件回退。若只想撤掉某个文件，建议新建一条变更或让同事调整分支后重新走流程。
- **基线漂移**：同事分支基于旧 `main` 时，若 `main` 在基线后改过同一文件，脚本会阻止直接应用；推荐先让同事 `git rebase origin/main` 再重新提交审核，而不是强行覆盖。
- **构建环境差异**：脚本的构建检查使用本机 Swift SDK 与参数；构建通过只代表本机 release 构建通过，仍需按项目要求做真实运行/人工验收。

## 8. 回退（“回调”）步骤

```sh
git switch main
python3 变更管理/工具/回退变更.py --id CHG-20261023-01 --dry-run   # 预演
python3 变更管理/工具/回退变更.py --id CHG-20261023-01             # 正式回退
git push origin main        # 需要同步远程时手动执行
```

回退会：

1. 读取 `记录/<ID>/应用记录.json` 里最近一次未回退的应用；
2. 把采纳文件恢复到应用前版本、删除当时新增的文件、还原重命名；
3. 提交 `回退变更 <ID>`；
4. 更新记录与 `索引.md`（状态：已回退，回退时间：YYYY-MM-DD HH:MM）；
5. 打印：**源码已回退，需重新打包安装才生效。**

注意：

- 回退只恢复源码；**务必重新打包并替换安装版 App，回退才会真正生效**。
- 如果文件在采纳之后又被其它提交改动过，脚本默认停下；确认可以放弃这些改动后加 `--force`。
- 同一变更可再次采纳（应用记录会追加），再次采纳后仍可回退。
- 回退不会删除 `change/<ID>` 分支和记录，保留追溯。

## 10. 索引与记录的含义

- `索引.md`：所有变更的总表，脚本自动增行/更新状态；**不要手工改列顺序**。
  - 采纳文件数：`已采纳数/变更总数`（全部不采纳记为 `0/总数`）。
  - 回退时间：最近一次回退的 `YYYY-MM-DD HH:MM`；未回退为 `-`。
- `记录/<ID>/变更单.md`：人看的主文档，负责人标注采纳状态也在这里。
- `记录/<ID>/清单.json`：脚本读取的机器清单（基线 commit、分支、逐文件类型/行数/说明）。
- `记录/<ID>/改动.diff`：完整 diff，便于逐行审阅；不含二进制文件正文。
- `记录/<ID>/应用记录.json`：每次采纳的应用前提交、文件列表、构建说明、回退时间；**回退依赖它，不要手改/删除**。

`变更管理/` 属于流程元数据，不计入变更清单；同事请不要在变更分支里顺便改工具脚本，工具调整由负责人单独提交。

## 11. 禁止事项

- ❌ 直接向 `main` 推送未审核改动；直接合并 `change/` 到 `main` 绕过采纳流程。
- ❌ 把安装包（`.app`/`.zip`/`.dmg`）、验证证据（`macos/ProductValidation/`）、用户数据、密钥、token、示例资料库提交到私有源码仓库。
- ❌ 在变更里夹带无关格式化、批量重命名、依赖升级等“顺手改”。
- ❌ 手工修改 `清单.json` / `应用记录.json` 来绕过校验。
- ❌ 删除别人的 `记录/<ID>/` 或改动 `索引.md` 行顺序。
- ❌ 让脚本自动 push、自动打包、自动发布或联网（脚本本身不会，也不要改造成这样）。
- ❌ 用 `--allow-overwrite`/`--force` 掩盖基线冲突或回退冲突，除非明确知道后果。

## 12. 常见问题（FAQ）

**Q1：提示“基线漂移：变更基线不是当前 main 的祖先”怎么办？**
A：`main` 历史被改写或分支与当前 `main` 无共同历史。让同事在 `change/<ID>` 上执行 `git fetch origin && git rebase origin/main`，再运行 `提交变更.py` 刷新基线后重新审核；或基于当前 `main` 重新生成变更。不要强行继续。

**Q2：提示 main 在基线后改过同一文件？**
A：说明 `main` 已有更晚的改动，直接应用会覆盖。推荐让同事 rebase 后重新提交；确认覆盖是预期行为时才加 `--allow-overwrite`。

**Q3：部分采纳后构建失败怎么办？**
A：脚本会自动恢复工作区并中止、不提交。调整采纳状态（把引起失败的关联文件也改为不采纳，或让同事修好后重新提交），再重跑；也可以先与同事确认拆分变更。不会留下半应用状态。

**Q4：提示工作区不干净？**
A：`新建变更.py` 和 `审核应用.py` 都要求干净工作区（审核时允许本变更记录目录未提交）。请先提交/`git stash`/还原，再运行。

**Q5：找不到变更分支 `change/<ID>`？**
A：先 `git fetch origin`；确认同事已执行脚本打印的 push 命令且分支名正确；只有本地分支时可用 `--branch change/<ID>` 指定。

**Q6：本地与远程的 change 分支不一致？**
A：脚本无法判断哪一个是审核对象，会停止。确认最新提交后：删除/更新本地分支，或用 `--branch origin/change/<ID>` 明确指定。

**Q7：工作区记录与分支不一致（同事更新了分支）？**
A：加 `--refresh-record` 重新复制分支记录（**会丢失当前标注**），然后重新标注。

**Q8：变更单说明还是占位文字，无法提交？**
A：先运行 `提交变更.py --check-only` 看缺哪些文件；编辑变更单「说明」列或用 `--notes` 文件补齐后再提交。

**Q9：回退后 App 没变化？**
A：回退只恢复源码；需要重新打包并替换安装版 App，必要时重启应用。另确认 `git push origin main` 是否已让其它机器拿到回退提交。

**Q10：回退提示文件被其它提交改过？**
A：确认可以放弃这些后续改动后加 `--force`；否则先人工处理冲突，或对相关文件单独走新的变更流程。

**Q11：编号重复 / 分支已存在？**
A：`change/<ID>` 或记录目录已存在。换一个新编号（同一天序号 +1），不要覆盖旧记录。

**Q12：脚本会用网络吗？会碰生产数据吗？**
A：不会联网（不 fetch/push/上传）、不会启动 App、不会打包、不会改生产库；只操作当前 git 仓库的工作区与记录目录。

**Q13：能不能只回退某个文件？**
A：“回调”以变更为单位回退当时采纳的文件集合。只撤单个文件请新建一条变更，或手工处理后重新走审核流程（不建议直接改 `main`）。

**Q14：提交变更时提示“暂存区已有其它改动”？**
A：脚本要求暂存区干净，避免把无关内容带进提交。请先 `git commit` 或 `git restore --staged <路径>` 处理已有暂存内容，再运行。

**Q15：自测需要联网或 Swift 工具链吗？**
A：不需要联网（只用本地 bare 仓库模拟 origin）；构建相关的检查用“假 swift”模拟，不会真正执行 Swift 构建。只在 `/tmp` 下写临时仓库，跑完自动清理。
